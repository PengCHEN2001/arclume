# Arclume 路线图

本文区分 Arclume **已经实现的原型能力、公开展示前还要验证的事项，以及后续计划**。它不是变更流水，也不承诺完成日期；“已实现”不等于“已用真实业务数据验证”或“可投入生产”。

## 当前状态

Arclume 的客服后端主链路已经整合，并有第一版 Web 界面。项目目前适合本地运行、演示、学习和继续开发；尚不能据此视为已经具备生产环境所需的安全、数据治理和运营保障。

### 已完成的主要能力

| 领域 | 当前完成情况 |
|---|---|
| API 与应用运行 | 使用 FastAPI 提供健康检查、聊天、知识检索、知识导入、Skill、Trace、Monitor 和 Evaluation 等接口。 |
| 多 Agent | 支持 General、Technical、Billing 和人工升级流程；包含 Agent Profile、路由、复合请求协作及结果整合。 |
| RAG | 支持 ChromaDB 向量召回与 BM25 关键词召回、并行检索、RRF 融合、去重和重排；也包含查询变体、缓存、超时、重试、熔断与降级。 |
| Memory | Redis 保存会话工作记忆、摘要和 AgentState；ChromaDB 保存长期情景记忆与用户画像。 |
| Tool 治理 | Tool 经 Harness 统一执行，包含权限和风险检查、结果规范化、调用循环边界、统计与 Trace；高风险操作不会绕过审批边界直接执行。 |
| Skills | 支持人工维护的元数据、按 Agent 和关键词筛选、注入长度限制及热加载。 |
| Trace 与 Monitor | 支持请求级 Trace 查询、Agent/Tool 运行统计、路由调整信号，以及 Prometheus 格式的指标接口。 |
| Evaluation | 支持意图和路由分类指标、Precision/Recall/F1、RAG 排序指标、对话评测、可选 LLM Judge 和回归比较；已有 LLM 生成的合成意图样例与 18 条英文 RAG 检索题。尚无确认过的真实模型回答质量或当前知识库检索分数。 |
| Web 界面 | 已有由 AI 生成的 Vue/Vite 初版页面，覆盖对话、知识库和评测等操作；主要项目重点仍是后端链路，界面需要端到端联调。 |
| 本地基础设施 | 提供 Redis、ChromaDB、API、Prometheus 和 Nginx 的本地 Compose 配置。 |

当前能力中的重要限制：订单、物流和工单工具仍有 Mock/确定性实现；Trace 主要保存在进程内；演示知识库为 9 篇、约 18 个默认 chunk 的虚构英文资料；500 条意图评测数据为 LLM 生成的合成样例，尚未独立人工审核，不等同于经过外部验证的生产基准。

## 公开展示前的最小验证（尚待完成）

这些检查是为了让别人按 README 复现项目，而不是要求先做完下面所有生产化工作。

1. **跑通真实检索。** 用隔离的空 ChromaDB 建立当前 9 篇英文演示文档的索引，确认默认 Embedding 能完成入库和查询，检查 `/health` 与 `/knowledge/stats`，再执行 `rag-smoke-v3` 的 18 条检索题。记录实际配置、指标和失败样例；首次模型下载可能增加本地耗时，但检索评测不需要 Chat API Token。不要删除已有知识库来“清空重测”。
2. **做少量真实 `/chat` 演示。** 用可用的模型接口依次测试普通消息、退款政策、登录故障加重复扣费、人工转接；检查回答、`primary_agent`、`supporting_agents`、`tools_used` 和 Trace。多 Agent 会增加模型请求，先保持额外的 Intent/RAG/Memory LLM 开关关闭。测试成功才把行为写成对外可复现的演示结果。
3. **整理公开仓库。** 确认不公开的学习笔记、实验版本和密钥没有进入拟上传的文件及历史；README 的启动命令、文档链接和已实现/未实现说明与公开内容一致。运行单元测试，并只引用可复现、有边界说明的评测结果。

## 后续迭代方向

以下按工程依赖排序，实际优先级以真实测试暴露的问题为准。每个方向先形成可复现的失败样例，再决定是否增加新组件。

### 1. RAG：先管好资料，再比较检索方案

- 补知识文档的来源、产品型号、适用范围与版本元数据；设计更新/删除时清理旧 chunk、刷新 BM25 和重新生成评测标签的流程。
- 扩充少量人工审核的英文用例，覆盖相似商品、精确型号、政策例外、跨文档、无答案和旧信息干扰。分别比较 Dense、BM25、混合检索、查询改写和重排，记录 Recall@K/MRR/nDCG 与延迟。
- 在检索指标之外检查回答是否被片段支持、无证据时能否明确表示不确定。只有现有评测显示值得时，再试专用 reranker、其他 Embedding 模型或更复杂的索引；更换 Embedding 后必须重建向量索引。

### 2. Agent：验证路由与协作，而不是只增加角色

- 为主/辅助 Agent、RAG 启动、Tool 选择和拒绝/升级分别增加标注用例，重点检查多主题、否定、依赖历史和相似关键词误判。
- 检查多 Agent 回复是否重复或矛盾；必要时改进结果合并和失败回退。继续验证最终合并回复写回会话后的多轮连续性。
- 改进不完整短回复的多轮澄清。当前用户只回复 `yes`、`no`、`it`、`that`，或没有回答上一轮 A/B 选择时，本地路由可能因本轮缺少可靠业务主题而返回通用分类澄清（订单、退款、账户或技术问题）。这是一条安全回退，但不够贴合上下文。后续可结合最近一条 Assistant 的明确问题与 `AgentState`，生成针对性的追问；例如系统问“Mini、Pro，还是需要选择建议？”后，用户只答 `yes` 或给出无关内容时，应继续询问具体选项，而非猜测或跳转到通用分类。
- 为高风险操作设计真正的人工审批、拒绝、超时和恢复执行流程；在完成之前保持写操作不向 `/chat` Agent 开放。

### 3. LangChain / LangGraph：做可比较的第二种实现

- 在学习框架后，建立与现有主链路功能边界一致的独立版本：意图与路由、Memory、RAG、Tool 策略、人工升级和 Trace。它目前不是对外主实现，也不应在未经核对时宣称功能等价。
- 使用同一批请求和评测用例比较两种实现的可理解性、状态管理、失败恢复、延迟与模型调用次数。若只是“换框架”而没有明确收益，保留当前自建实现即可。

### 4. 真实业务接入与生产保障（长期方向）

- 把订单、物流和工单 Mock 换成可配置的业务适配器；真实写操作需要身份校验、幂等、防重复提交与审计。
- 明确认证、权限、租户隔离、限流、CORS、密钥管理，以及对话、画像和 Trace 的保留与删除规则。
- 评估持久化 Trace、告警、资源限制和部署恢复；目标值应来自实际使用场景，不在原型阶段臆定。
- 前端继续作为演示入口：先验证与后端 API 的连接、加载与错误状态，再决定是否投入更多界面开发。

## 暂不列为当前承诺

- 自动生成、修改、发布或回滚 Skills。
- 为了扩展数量而增加更多 Agent；新增 Agent 应由真实业务场景驱动。
- 接入外部 MCP 协议。当前重点是把项目内部的 Tool 边界和治理做好。
- 宣称当前评测分数代表生产准确率，或宣称系统已经达到生产级就绪状态。

## 进度维护规则

- 完成一项验证或方向发生变化时，更新对应状态与证据；不要把尚未实施的想法写成现有能力。
- README 保持项目简介、快速启动和已知边界；本路线图只记录下一步，不充当代码变更流水。
