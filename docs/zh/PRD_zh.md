本文定义 Arclume 要解决的问题、目标用户、产品范围、关键体验和验收标准。技术实现与当前完成情况会单独标明；“已有原型实现”不等于达到上线要求。

## 1. 产品概述

Arclume 是一个面向电商客服场景的多 Agent AI 辅助服务系统。首版聚焦英文客服对话，后续计划演进为支持多语言的客服处理能力。

真实顾客不会按系统预设分类提问：一条消息可能同时包含商品咨询、登录故障、退款或物流问题，也可能依赖前文语境。Arclume 不将整段消息直接交给单一模型回答，而是先识别其中涉及的领域、所需信息和风险等级，再制定处理计划：由一个或多个职责明确的 Agent 协作处理；按需查询知识库或受控业务工具；最后整合为一条完整、可追踪的回复。

产品重点是让系统能够**有依据、可控制地处理复杂客服信息**，而不是让模型自由生成或不受约束地执行操作。信息不足时，系统应继续澄清；涉及高风险操作或用户要求人工协助时，应说明限制并进入升级流程。

多语言演进不应只停留在界面翻译。后续需要验证不同语言下的意图识别、知识检索、术语一致性、Agent 路由和评测数据是否仍然可靠。

## 2. 背景、问题与产品假设

客服消息不一定只属于一个领域。例如，顾客可能同时报告登录失败和重复扣费；询问退款规则时需要政策依据，查询订单当前状态时则需要业务数据。若所有问题都交给一个没有明确证据边界的回答流程，可能出现答非所问、编造政策、把历史知识当作实时状态或错误执行工具等问题。

本产品基于以下待验证假设：

1. 按领域分工并整合结果，有助于提高复合问题的回答完整性。
2. 明确区分知识问题与实时业务数据请求，有助于减少无依据回答及不必要的工具调用。
3. 保存请求级处理记录，有助于发现错误、复现问题和比较改进效果。

这些仍是**产品假设**。真实顾客的问题分布、痛点严重程度和使用意愿尚未通过用户研究或线上数据验证，验证方法与负责人【待定】。

## 3. 目标用户与使用场景

| 用户角色 | 主要需求 | 当前优先级 |
| --- | --- | --- |
| 顾客 | 获得准确、易懂的答复；无法解决时知道下一步如何处理 | 首要用户 |
| 客服或运营人员 | 查看需人工处理的问题，维护系统所依赖的知识内容 | 次要用户；具体工作流【待定】 |
| 产品与技术运营人员 | 检查请求处理过程、发现错误并评估质量 | 次要用户 |

首版优先考虑以下场景：普通咨询；退款、配送和商品等知识问题；账户或账单问题；一条消息中的多个独立问题；需要查询当前业务状态的只读请求；用户明确要求人工协助。

首版客服消息以英文为范围。实际接入渠道、目标顾客群、服务地区及其他语言支持【待定】。

| 提供准确、完整的答复 | 人工审核的正确性、完整性、证据一致性 | 尚无经过确认的端到端回答质量基线 | 【待定】 |
| 安全处理复杂请求 | 复合问题覆盖率、不必要工具调用率、高风险操作阻断情况 | 原型具备相关机制；尚未完成充分的场景验收 | 【待定】 |

正式目标值必须基于人工审核的测试数据和确定的使用规模制定。原型的离线分数不能作为对顾客的服务承诺。

## 5. 首版范围与非目标

### 5.1 首版范围

- 接收顾客消息，并在同一会话中延续必要的上下文。
- 判断问题领域、关键信息及所需证据类型。
- 将单领域或多领域问题交给相应流程处理，并形成一条完整回复。
- 对政策和商品问题检索知识；对当前状态请求考虑受权限约束的只读业务查询。
- 对信息不足、明确人工诉求或高风险操作给出适当的澄清、拒绝或升级结果。
- 保留关键处理记录，支持排查问题和重复评估。
- 提供知识维护与质量评估的基本入口。

### 5.2 当前非目标

- 自动完成退款、支付或其他高风险写操作。
- 提供已经接通真实客服人员的人工转接服务。
- 接入真实订单、物流、支付或工单系统。
- 在尚未确定运行环境前承诺生产级可用性、性能、隐私合规或多租户能力。
- 在首版支持英文以外的客服交互语言。

上述非目标界定的是当前版本边界，不代表未来不需要这些能力。

## 6. 关键用户流程

### 6.1 政策或商品知识问题

顾客询问“退款政策是什么”。系统应判断回答需要知识依据，检索相关内容，再基于获得的内容作答。如果没有可靠依据，应说明无法核实，并给出下一步建议，而不是编造政策期限或条件。是否向顾客显示引用来源及其呈现方式【待定】。

### 6.2 多领域复合问题

顾客同时提出“无法登录”和“被重复扣费”。系统应识别两个独立问题，分别处理后返回一条连贯回复，不能遗漏其中一个问题，也不能在未查询到真实支付记录时声称已核实扣费。下一轮对话应能参考这条最终合并回复。

### 6.3 当前业务状态查询

顾客询问某笔订单在哪里。系统应区分订单的**当前状态**与一般配送政策；只有获得授权的业务查询结果，才能作为实时状态依据。依赖不可用时，应明确表示无法核实，不得猜测订单状态。目前原型使用模拟业务数据，不能将其展示为真实顾客记录。

### 6.4 人工协助或高风险操作

顾客明确要求人工时，系统应确认诉求并说明可用的后续路径。高风险操作在缺少必要批准时不得执行。在实际人工服务接入前，系统不得声称已经创建真实工单或接通客服。接收团队、渠道、服务时间、时限和审批流程【待定】。

## 7. 功能需求与验收标准

P0 表示完成核心顾客流程所必需；P1 表示支持运营和持续改进。以下写的是**产品需求**，不是对当前代码完成度的判断。

| 编号 | 优先级 | 需求 | 可观察的验收标准 |
| --- | --- | --- | --- |
| FR-01 | P0 | 接收消息并延续会话 | 返回答复、会话标识和请求标识；后续同一会话能利用相关历史 |
| FR-02 | P0 | 识别问题和所需信息 | 能区分普通对话、知识问题、实时数据请求、复合问题和明确人工诉求；不确定时有澄清或复核路径 |
| FR-03 | P0 | 选择合适的处理路径 | 将问题交给适当的一个或多个领域流程；处理选择可供事后检查 |
| FR-04 | P0 | 基于知识回答 | 需要知识时检索相关资料；无可靠结果时不声称找到了依据 |
| FR-05 | P0 | 管控业务工具 | 工具使用遵守职责、参数和风险约束；未经批准的高风险操作不能执行 |
| FR-06 | P0 | 形成单一完整回复 | 多领域问题的各部分得到回应；最终回复可用于后续会话，而不仅保存中间结果 |
| FR-07 | P0 | 澄清或升级 | 无法可靠回答或用户要求人工时，给出准确的下一步；不虚构已完成的转接 |
| FR-08 | P1 | 维护知识内容 | 运营人员可添加或查看知识并验证检索；审核、发布、版本与回滚标准【待定】 |
| FR-09 | P1 | 观察和评估系统 | 能按请求检查关键决策并重复运行路由、检索和回答评估；执行失败与有效分数明确区分 |
| FR-10 | P1 | 提供交互界面 | 核心顾客流程能够通过界面完成；最终渠道、设计与无障碍要求【待定】 |

## 8. 交互与内容要求

- 回复应使用顾客易懂的语言，覆盖顾客实际提出的问题。
- 应区分“系统已执行的操作”“系统建议顾客采取的操作”和“系统无法核实的信息”。
- 缺少证据时应限定说法、请求补充信息或升级，不能编造政策、订单或支付事实。
- 顾客是否看到知识来源、处理状态、工具结果及其详细程度【待定】。
- 回复语气、长度、移动端适配与无障碍标准【待定】。
- 客服人员查看升级请求和纠正知识内容的界面与操作流程【待定】。

## 10. 验证与发布条件

在确认首版达到要求前，应完成以下验证：

1. 对普通咨询、知识问题、多领域问题、当前状态查询、澄清和人工诉求逐一进行端到端测试，记录请求标识与实际结果。
2. 固定英文知识内容、切片与检索配置，使用审核过的样例测量召回和排序质量，并检查无答案与过期信息场景。
3. 人工核对模型答复是否正确、完整且与取得的证据一致；检查依赖故障和工具拒绝时的回复。
4. 验证未经批准的高风险操作被阻断，模拟业务结果不会被误认为真实记录。
5. 确定独立保留测试集、各项指标门槛、发布审批人及回退条件：**【待完善】**。

试点范围、分阶段发布方式、运行监控责任人与正式上线条件【待定】。

## 11. 当前原型与尚未满足的要求

现有原型包含聊天接口、意图与路由、多领域处理、会话记忆、知识检索、受控工具执行，以及请求记录和评估入口。但这些实现尚不足以证明前述产品指标已经达成。

- 演示知识规模较小；当前标注检索集还没有经过确认的实际运行分数。
- 订单、物流与工单相关工具包含模拟或确定性行为，不代表真实业务记录。
- 人工升级尚未连接实际客服流程；聊天主链路也没有完整的高风险操作批准后恢复执行机制。
- 请求记录主要保存在进程内；正式鉴权、数据治理和持久化尚未完成。
- 交互界面、真实模型回答质量和依赖故障下的完整体验仍需端到端验证。

“存在实现”和“满足验收标准”应分开判断。每项需求的最终状态应由对应的验收证据确认。
