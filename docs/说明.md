# Arclume 项目完整学习说明

这份文档是 Arclume 当前代码的总说明，目标不是只告诉你“某个文件在哪”，而是帮助你建立下面这张完整的心智地图：

```text
用户请求
  ↓
FastAPI 接口
  ↓
请求数据校验
  ↓
IntentRecognizer 意图识别
  ↓
AgentOrchestrator 路由
  ↓
选择 AgentProfile、Skill 和 Tool 范围
  ↓
CustomerServiceAgent 构建 Context
  ↓
Memory / RAG / Skill / Tool / LLM
  ↓
生成 Agent 回复
  ↓
写回 Memory，记录 Trace 和 Monitor 指标
  ↓
返回 API 响应
```

如果你第一次看这个项目，不建议从 `api/main.py` 直接从第一行读到最后一行。
推荐先看本文的“学习顺序”，再按照每个模块的职责去看代码。

---

## 一、先用一句话理解整个项目

Arclume 是一个面向客服场景的多 Agent 系统：

- 先识别用户到底在问什么；
- 再决定交给 General、Technical、Billing 还是 Escalation Agent；
- Agent 根据需要读取 Redis 记忆、ChromaDB 知识库、Skills 和业务 Tools；
- Harness 负责 Tool 的权限、风险、超时、重试、缓存、熔断、Fallback 和 Trace；
- Monitor 观察线上运行状态；
- Evaluation 离线判断修改以后质量有没有变好。

它不是只有一个大模型 Prompt。大模型只是其中的一个执行组件，外围的路由、上下文、记忆、检索、工具治理和评测，都是独立的工程模块。

## 二、先看整体架构

### 1. 运行时主链路

用户调用：

```http
POST /chat
```

请求会经过：

```text
api/main.py
  → ConversationMemory 读取 Redis 工作记忆
  → AgentOrchestrator.run()
      → IntentRecognizer.recognize()
      → _make_decision()
      → 选择一个或多个 Agent
      → CustomerServiceAgent.respond()
          → ContextBuilder.build()
          → 读取 Skill
          → 需要时调用 knowledge_search
          → 需要时进入 Agent Tool Call Loop
          → 调用 LLMClient
      → ResponseComposer 合并多个 Agent 的结果
  → 返回 ChatResponse
```

同时，Trace 会记录：

```text
请求开始
→ Intent 识别
→ 路由选择
→ Skill 选择
→ RAG 完成
→ Agent 开始 / 完成
→ Tool 执行
→ Memory 更新
→ 请求完成
```

### 2. RAG 主链路

业务问题进入知识检索时，当前主链路是：

```text
判断是否需要 RAG
  → 查询改写
  → Dense 向量召回
  → BM25 关键词召回
  → 并行分支返回
  → RRF 合并排名
  → chunk 去重
  → 本地重排或可选 LLM 重排
  → 截取 Top-K
  → 注入 Agent Context
```

Dense 检索使用 ChromaDB，解决“用户说法和文档原话不同”的问题。

BM25 检索在进程内运行，解决订单号、错误码、专有名词和精确关键词问题。

当前的本地重排会综合：

- RRF 融合分数；
- 查询和 chunk 的词汇重叠；
- BM25 分数；
- Dense 分数。

如果显式打开 `ARCLUME_RAG_LLM_ENABLED=true`，才会额外请求模型做 LLM rerank。

### 3. Memory 分层

当前的 Memory 不是一个数据库包打天下，而是分层保存：

```text
Redis
  ├── 最近几轮会话消息
  ├── 当前会话 summary
  └── AgentState

ChromaDB
  ├── episodic：被压缩的历史对话摘要
  └── user_profile：用户偏好和关键实体
```

Redis 保存“当前工作记忆”，ChromaDB 保存“需要长期召回的语义记忆”。

### 4. Tool 治理边界

Agent 或模型不能直接随意调用 Python 函数。调用路径是：

```text
模型提出 ToolCall
  → HarnessRuntime
  → ToolPolicy 判断允许、拒绝还是需要审批
  → ToolExecutor / ToolManager 执行
  → 参数校验、超时、重试、缓存、熔断、Fallback
  → 统一 ToolResult
  → 写入 Trace
```

这就是为什么项目里既有 `tools/`，又有 `harness/`：

- `tools/` 负责 Tool 具体做什么；
- `harness/` 负责 Tool 能不能做、怎么安全地做。

## 四、根目录文件

### `README.md`

项目总览和当前阶段说明。它适合快速确认：

- 项目是什么；
- 当前已经有哪些能力；
- 如何创建虚拟环境；
- 如何启动 API；
- 如何启动 Docker；
- 有哪些 HTTP 接口；
- Redis 和 ChromaDB 分别做什么。

README 是入口地图，不是每个模块的详细教程。细节应当回到对应的 Python 文件和 `docs/step*.md`。

### `.env.example`

环境变量模板。它只放配置名和示例值，不应该放真实 API Key。

主要分为：

```text
模型配置：LLM_PROVIDER、LLM_API_KEY、LLM_BASE_URL、LLM_MODEL
Intent / RAG：ARCLUME_INTENT_LLM_ENABLED、ARCLUME_RAG_LLM_ENABLED、ARCLUME_RAG_BM25_ENABLED
Memory：REDIS_URL、ARCLUME_MEMORY_COMPRESS_AT、ARCLUME_MEMORY_RETAIN_MESSAGES
ChromaDB：CHROMA_HOST、CHROMA_PORT、CHROMA_PERSIST_DIRECTORY、CHROMA_CHUNK_SIZE
运行时：ARCLUME_SKILLS_DIR、ARCLUME_TRACE_MAX_EVENTS、ARCLUME_EVAL_BASELINE_PATH
Monitor：ARCLUME_MONITOR_ENABLED、PROMETHEUS_PORT
```

最重要的开关是：

- `ARCLUME_INTENT_LLM_ENABLED=false`：默认先用本地 Intent 识别；
- `ARCLUME_RAG_LLM_ENABLED=false`：默认先用本地查询改写和本地重排；
- `ARCLUME_RAG_BM25_ENABLED=true`：默认使用混合检索；
- `ARCLUME_MEMORY_LLM_ENABLED=false`：默认使用本地 Memory 压缩，避免额外模型调用。

### `.gitignore`

告诉 Git 哪些内容不应提交，例如 `.env`、`.venv`、Python 缓存、ChromaDB 数据和日志。

### `.dockerignore`

告诉 Docker 构建镜像时哪些本地文件不复制进去，避免把虚拟环境、缓存和 Git 信息打包进镜像。

### `requirements.txt`

Python 依赖清单：

```text
FastAPI / Uvicorn       HTTP 服务
Pydantic                数据校验
httpx                   异步调用 OpenAI-compatible 模型
redis                   Redis 客户端
chromadb                ChromaDB 客户端
prometheus-client       Prometheus 指标
python-multipart        文件上传
python-dotenv           读取 .env
```

### `Dockerfile`

构建 Arclume API 镜像：使用 Python 3.10，安装依赖，复制后端运行代码，最后用 Uvicorn 启动 `api.main:app`。它不负责构建 Vue 前端。

### `docker-compose.yml`

定义本地部署所需的服务：

```text
api / redis / chromadb / prometheus / nginx
```

其中 API 是应用，Redis 是工作记忆和 AgentState，ChromaDB 是知识库和长期语义 Memory，Prometheus 采集指标，Nginx 负责反向代理。Compose 还配置健康检查、数据卷、Redis 密码和 Evaluation baseline 挂载。

## 五、`schemas/`：所有模块共享的数据契约

这个目录只定义数据结构，不负责业务流程，类似系统中的“接口协议层”。

### `schemas/api.py`

定义 HTTP 请求和响应模型：

- `ChatRequest`：`/chat` 的输入，包括 message、user_id、conversation_id；
- `ChatResponse`：回复、Intent、主 Agent、辅助 Agent、Trace 和 Tool 信息；
- `KnowledgeDocumentInput`、`KnowledgeBatchInput`：知识库导入数据；
- `EvalIntentCaseInput`、`EvalDialogCaseInput`、`EvalRunInput`：评测接口的输入。

这里的模型负责输入校验，例如 message 不能为空、置信度必须在 0 到 1 之间。

### `schemas/context.py`

定义一次模型请求的临时上下文：

- `ContextMessage`：一条 system/user/assistant/tool 消息；
- `Context`：当前问题、历史消息、summary、episodic memory、用户画像、AgentState、知识结果、Skill 指令和 Tool 结果。

`Context` 是一次请求的上下文，不等于长期 Memory。Memory 负责保存和读取，ContextBuilder 负责组合。

### `schemas/state.py`

定义 `AgentState`，表示一个正在处理的客服案件：用户和会话、当前状态、Intent、紧急度、当前 Agent、是否需要 RAG、是否等待人工或审批，以及版本号。

它最终通过 `memory/state_store.py` 保存到 Redis。

### `schemas/tool.py`

定义：

- `ToolCall`：谁请求哪个 Tool，以及参数是什么；
- `ToolResult`：Tool 是否成功、数据、错误、耗时、缓存、Fallback、重排和审批状态。

这里仅描述数据，风险判断在 `harness/policy.py`，实际执行在 `harness/executor.py`。

### `schemas/__init__.py`

包说明文件，表明 `schemas/` 是 Arclume 共享数据契约包。本身不承担业务逻辑。

## 六、`core/`：系统的基础智能组件

### `core/__init__.py`

包说明文件，表明 `core/` 是基础应用工具包，本身不执行一次完整请求。

### `core/llm_utils.py`

这是模型传输层，不是 Agent 框架。

- `LLMSettings`：从环境变量读取 provider、API Key、Base URL、模型和超时；
- `LLMClient`：通过 OpenAI-compatible `/chat/completions` 发送普通文本或 Tool Calling 请求；
- `LLMToolCall`、`LLMToolResponse`：规范化模型提出的函数调用和返回；
- `LLMConfigurationError`、`LLMRequestError`：分别表示配置问题和请求问题。

这个文件不决定何时查知识库、选哪个 Agent、哪个 Tool 可以调用或 Memory 怎么保存。

### `core/intent_recognizer.py`

这是意图识别模块。

- `IntentCategory`：细粒度 Intent，例如 `refund`、`payment_issue`、`technical_login`、`human_handoff`；
- `UrgencyLevel`：low、medium、high、critical；
- `IntentResult`：最终 Intent、Intent group、置信度、紧急度、实体、来源分数、领域分数、匹配候选和 RAG 开关；
- `IntentRecognizer`：执行识别、缓存、人工学习和可选模型 refinement。

它可以综合三类信息：

```text
Pattern / 本地规则
本地向量相似度
可选 LLM refinement
```

默认不调用模型，只有打开 `ARCLUME_INTENT_LLM_ENABLED` 才会增加模型调用。

重要方法：`recognize()`、`learn()`、`clear_cache()`、`cache_stats()`、`_pattern_scores()`、`_embedding_match()`、`_llm_match()`、`_fuse()`、`_detect_urgency()` 和 `_extract_entities()`。

### `core/context_builder.py`

负责把不同来源的信息组装为一个 `Context`：

```text
当前问题 + 最近对话 + Redis summary + ChromaDB episodic memory
+ 用户画像 + AgentState + 知识库结果 + Skill 指令 + Tool 结果
```

核心方法：

- `build()`：创建结构化上下文；
- `render_system_prompt()`：渲染系统指令；
- `render_history()`：把状态、Skill、Memory、知识和历史消息转成模型消息。

它不负责读数据库，也不负责调用模型，只负责整理已经拿到的数据。

### `core/skill_loader.py`

负责读取和选择人工维护的 Skill 文件。

- `SkillDocument`：名称、描述、正文、路径、关键词、适用 Agent、是否启用；
- `load()`、`load_many()`：读取 Skill；
- `list_skills()`、`list_available()`：列出 Skill；
- `select_for_agent()`：按 Agent、关键词和显式名称筛选；
- `render()`：渲染 Prompt 片段；
- `reload()`：重新加载文件；
- `summary()`：向 API 返回不包含正文的安全摘要。

它只读取人工写的文件，不会让模型自动生成、修改、发布或回滚 Skill。

## 七、`harness/`：Tool 的安全执行边界

### `harness/policy.py`

只负责“能不能执行”，不负责实际执行。

- `ToolRiskLevel`：low、medium、high；
- `PolicyAction`：allow、deny、require_approval；
- `PolicyResult`：规则决定和原因；
- `ToolPolicy`：根据 Tool 是否存在、是否启用、Agent 是否有权限、风险等级和允许列表做判断。

例如 `ticket_create` 是 high risk，Policy 可以返回 `require_approval`，而不是直接写入业务系统。

### `harness/executor.py`

负责执行已经通过基础检查的 Tool。

- `ToolDefinition`：Tool 名称、描述、处理函数、参数 Schema、风险、超时、重试、允许 Agent、缓存 TTL、Fallback；
- `ToolExecutor`：注册、注销、查询、列出和执行 Tool。

`ToolDefinition` 是 Tool 治理的元数据中心，业务函数不用重复实现超时、重试和统一结果格式。

### `harness/runtime.py`

`HarnessRuntime` 连接 Policy、Executor、Trace 和 Agent 决策循环：

1. 接收 ToolCall 或模型决策；
2. 检查最大循环次数；
3. 调用 ToolPolicy；
4. 必要时等待审批；
5. 调用 ToolExecutor；
6. 记录 Policy、执行和完成事件；
7. 返回 `RuntimeOutcome`。

它不是完整 Agent Brain，而是“让模型在受控边界内使用 Tool”的运行骨架。

### `harness/trace.py`

定义请求级 Trace：

- `TraceEventType`：请求、Intent、路由、Skill、RAG、Agent、Tool、Memory、完成等事件；
- `TraceEvent`：事件 ID、时间、request_id、conversation_id、Agent、Tool 和附加数据；
- `TraceRecorder`：保存有上限的事件，支持按 request_id 查询和清理。

Trace 默认是有界内存存储，适合本地调试和当前进程内诊断，不是永久日志数据库。

### `harness/__init__.py`

包说明文件，表明 `harness/` 是 Agent 运行时的执行控制层。
Trace 默认是有界内存存储，适合本地调试和当前进程内诊断，不是永久日志数据库。

## 八、`knowledge/`：知识库和 RAG 底层

### `knowledge/knowledge_base.py`

这是 ChromaDB 知识库适配器，负责：

- 连接远程 ChromaDB 或本地 Fallback；
- 把文档切成 chunk；
- 保存 title、source、chunk_index、total_chunks 和内容；
- 为 chunk 创建 embedding 并写入 ChromaDB；
- 根据查询返回语义相近的 chunk；
- 返回知识库状态、文档数量和索引内容。

文档进入知识库的大致过程：

```text
原始文档
  → 按 CHROMA_CHUNK_SIZE 切分
  → 每个 chunk 加元数据
  → ChromaDB embedding
  → 保存到 collection
```

chunk 不是单独的关键词，也不是只保存一句话，而是一段带来源和位置元数据的可检索文本。

### `knowledge/bm25_index.py`

这是进程内的 BM25 关键词索引，不依赖额外搜索服务。

`BM25Index` 负责：

- 保存 chunk 文档；
- 对文本进行 token 化；
- 统计词频、文档频率和平均文档长度；
- 根据查询计算 BM25 分数；
- 返回带 lexical score 的 chunk。

默认参数是 `k1=1.5` 和 `b=0.75`。Token 规则包括英文/数字连续 token 和中文单字 token。当前项目以英文为主，所以中文分词不是当前重点；后续可以换成专业中文分词器。

### `knowledge/hybrid_retriever.py`

这是 Dense 和 BM25 的混合检索层：

```text
ChromaDB dense branch
BM25 lexical branch
        ↓ 并行执行
RRF 融合排名
        ↓
按照 chunk_id 合并相同结果
        ↓
返回每个 chunk 的来源和融合分数
```

这里不负责最终的 LLM rerank，LLM rerank 在 `tools/tool_manager.py` 中由完整 Tool/RAG 流程控制。

### `knowledge/__init__.py`

定义 Knowledge 层的公共异常，例如知识库不可用或检索失败。它不保存知识数据本身。

## 九、`tools/`：Tool 具体实现和 RAG 编排

### `tools/tool_functions.py`

这里放当前项目的具体 Tool 函数。

#### 共享知识库 Tool

- `knowledge_search()`：调用现有 ToolManager 检索知识；
- `knowledge_search_fallback()`：知识服务不可用时返回明确的降级结果。

#### General Agent 专属 Tool

- `inspect_request_context()`：查看规范化请求上下文；
- `suggest_required_fields()`：提示业务请求缺少哪些字段。

#### Technical Agent 专属 Tool

- `lookup_error_code()`：根据错误码返回初步说明；
- `build_diagnostic_plan()`：构建诊断步骤。

#### Billing Agent 专属 Tool

- `check_billing_fields()`：检查账单或退款字段；
- `compare_amounts()`：比较金额。

#### Escalation Agent 专属 Tool

- `create_handoff_summary()`：生成转人工摘要。

#### 业务演示 Tool

- `order_query()`：订单查询演示；
- `logistics_query()`：物流查询演示；
- `ticket_create()`：工单创建演示，属于高风险操作。

最后的 `register_tools()` 把函数包装成 `ToolDefinition`，注册到共享 Executor。

要区分：这些函数是“Tool 做什么”；是否允许执行由 Harness 决定。

### `tools/tool_manager.py`

这是 Tool 的高级管理器，也是完整 RAG 主链路的编排位置。

它在 `ToolExecutor` 之上增加：

- Tool 统计；
- TTL 缓存；
- Circuit Breaker；
- Fallback；
- 查询改写；
- Dense + BM25 并行召回；
- RRF 融合；
- 去重；
- 本地重排；
- 可选 LLM 重排；
- RAG 和 Tool 的可靠性信息。

关键方法：

- `initialize_async()`：初始化混合检索索引；
- `execute()`：执行 Tool，并处理缓存、超时、重试、熔断和统计；
- `search_with_rewrite()`：运行完整 RAG 检索主链路；
- `rewrite_query()`：优先使用 LLM，否则调用本地规则生成变体；
- `rerank()`：优先可选 LLM 重排，否则使用本地排序；
- `_deduplicate()`：按照 chunk_id 去重；
- `_local_rerank()`：使用可解释的本地分数重排；
- `_local_query_variants()`：不调用模型时生成查询变体。

所以，`search_with_rewrite()` 放在 ToolManager，是因为知识库搜索被暴露为受治理的低风险 Tool。不是说查询改写本身就是 Tool 函数，而是 ToolManager 统一负责 Tool 执行可靠性和 RAG 编排。

## 十、`memory/`：Redis、ChromaDB 和 AgentState

### `memory/conversation_memory.py`

管理当前会话的工作记忆，主要保存：

- 最近消息；
- 当前会话摘要；
- 从长期 Memory 检索到的 episodic 记录；
- 用户画像。

消息超过阈值时：

```text
旧消息超过 ARCLUME_MEMORY_COMPRESS_AT
  → 保留最近 ARCLUME_MEMORY_RETAIN_MESSAGES 条
  → 旧消息生成 summary
  → summary 写回 Redis
  → 可选写入 ChromaDB episodic
```

默认优先使用本地事实压缩，只有打开 `ARCLUME_MEMORY_LLM_ENABLED` 才会额外调用模型。

### `memory/long_term_memory.py`

负责 ChromaDB 中的长期语义记忆：

- `episodic` collection：历史对话摘要；
- `user_profile` collection：用户偏好和关键实体。

它和知识库使用不同 collection，不应该把客服政策文档和用户个人记忆混在一起。

### `memory/state_store.py`

负责把 `AgentState` 保存到 Redis。

```text
ConversationMemory：用户说过什么
StateStore：当前案件处于什么状态
```

例如当前被哪个 Agent 处理、是否已经升级、是否等待补充信息、是否等待高风险操作审批。

### `memory/__init__.py`

定义 Memory 层的公共错误类型，例如 Redis 或长期 Memory 不可用时使用的异常。

## 十一、`skills/`：人工维护的运行规范

每个 Skill 目录包含一个 `SKILL.md`。Skill 不是模型，也不是 Python 函数，而是一份运行时注入的业务规范。

### `skills/refund/SKILL.md`

退款和支付规范：判断退款资格和处理时间，需要时询问订单号，不在没有业务结果时声称退款已经批准；退款、赔偿和账户变更可能需要 Tool 或人工审批。

### `skills/logistics/SKILL.md`

物流、配送、追踪和地址修改规范：区分通用配送政策和具体订单查询，具体查询前先要订单号或追踪号，不编造物流事件和送达时间，地址未得到业务系统确认时不能声称已经修改。

### `skills/technical/SKILL.md`

技术排障规范：收集产品、设备、环境、错误码和复现步骤，给出可逆且有顺序的排查步骤，不索要密码、验证码和私钥，发现安全、数据丢失或疑似大面积故障时升级。

### `skills/escalation/SKILL.md`

转人工规范：识别升级原因，总结已经知道的事实和做过的动作，告诉用户下一步；没有 Tool 确认时不能声称人工工单已经创建。

每个 Skill 的元数据包括：

```text
name / description / keywords / agents / enabled
```

`SkillLoader` 会根据 Agent、关键词和显式名称决定是否注入，并限制注入长度，避免 Skill 无限膨胀 Prompt。

## 十二、`agents/`：多 Agent 角色和编排

### `agents/agent_profile.py`

定义 `AgentProfile`，把一个 Agent 从“一个 Prompt”升级成结构化角色：

- role：角色；
- mission：任务；
- workflow：工作流；
- input_contract：输入契约；
- output_contract：输出契约；
- handoff_conditions：升级条件；
- tool_scope：可用 Tool；
- temperature、max_tokens：模型参数。

### `agents/customer_service_agent.py`

所有业务 Agent 的共享执行基类。`respond()` 大致负责：

1. 检查消息和 conversation_id；
2. 读取或写入会话 Memory；
3. 创建或更新 AgentState；
4. 根据 Agent Profile 准备 Tool 范围；
5. 需要时调用知识库；
6. 选择 Skill 并渲染 Prompt；
7. 用 ContextBuilder 构建上下文；
8. 直接调用模型，或进入受限 Tool Call Loop；
9. 保存 Assistant 回复；
10. 记录 Tool 和 Trace 信息。

这是“真正执行一次 Agent 回复”的地方。

### `agents/general_agent.py`

处理问候、一般问题、订单物流、不明确问题和其他 Agent 无法确定时的兜底。通常可以使用知识库、订单查询、物流查询和字段提示 Tool。

### `agents/technical_agent.py`

处理登录失败、错误码、应用崩溃、配置问题和技术排障，强调安全、可验证和按顺序的诊断步骤。

### `agents/billing_agent.py`

处理退款、发票、重复扣款、账单和账户相关账务问题，避免在没有业务系统确认时承诺退款或账户变更。

### `agents/escalation_agent.py`

处理转人工和高风险升级。它生成安全的交接说明，保存案件上下文，并告诉用户下一步，不让模型凭空声称后端操作已经完成。

### `agents/response_composer.py`

当一个复合问题需要多个 Agent 时合并结果：主 Agent 在前，辅助 Agent 在后，不再额外调用一次模型做合并。

### `agents/agent_orchestrator.py`

这是多 Agent 的总调度器。

核心类型：

- `AgentType`：general、technical、billing、escalation；
- `AgentStats`：总请求、成功数、平均延迟和 Monitor 惩罚；
- `AgentResponse`：单个 Agent 的内部结果；
- `RoutingDecision`：主 Agent、辅助 Agent、原因、置信度和 RAG 开关；
- `OrchestratorResult`：最终给 API 的结果。

`run()` 的主要步骤：

1. 创建 request_id；
2. 记录请求开始；
3. 调用 IntentRecognizer；
4. 判断是否需要澄清；
5. `_make_decision()` 选择主 Agent 和辅助 Agent；
6. 复合问题可以并行运行 Technical 和 Billing；
7. 调用 Agent；
8. 失败时执行兜底；
9. 用 ResponseComposer 合并；
10. 更新 Agent 统计和 Trace；
11. 返回 `OrchestratorResult`。

`update_routing_penalties()` 接收 Monitor 计算出的惩罚，让表现变差的 Agent 在后续路由中降低分数。

### `agents/__init__.py`

包说明文件，表明 `agents/` 是多 Agent 角色和编排代码包。本身不执行路由。
`update_routing_penalties()` 接收 Monitor 计算出的惩罚，让表现变差的 Agent 在后续路由中降低分数。

## 十三、`monitor/`：线上运行监控

### `monitor/performance_monitor.py`

Monitor 观察运行过程中的健康情况，而不是判断自然语言回答是否正确。

主要监控：

- Agent 成功率；
- Agent 平均耗时；
- Tool 成功率；
- Tool 平均耗时；
- 连续失败次数；
- 熔断状态；
- RAG 使用情况；
- 路由统计。

它会生成 alerts、suggestions 和 routing penalties。routing penalty 会反馈给 `AgentOrchestrator`，影响后续 Agent 选择。它也可以通过 `/metrics` 返回 Prometheus 格式数据。

要区分：

```text
Monitor：线上运行得是否健康
Evaluation：离线质量是否变好
```

一个 Agent 即使成功率是 100%，也可能一直回答错误；这个问题要靠 Evaluation 发现。

### `monitor/__init__.py`

包说明文件，表明 `monitor/` 是线上运行观测模块。

## 十四、`evaluation/`：质量评测和回归检测

### `evaluation/models.py`

定义离线评测输入输出：

- `IntentCase`：Intent 和可选 Agent 标注；
- `RetrievalCase`：查询、相关 chunk_id 和 top_k；
- `EvaluationReport`：通用 JSON 报告；
- `RegressionIssue`：某个指标退化；
- `RegressionReport`：baseline 与当前报告的比较结果；
- `EvaluationDataset`：从 JSON 读取 Intent 和 RAG 用例。

### `evaluation/metrics.py`

实现不依赖外部库的纯 Python 指标：

#### 分类指标

- `classification_accuracy()`；
- `macro_f1()`；
- `classification_metrics()`；
- `classification_details()`：同时返回每类 Precision、Recall、F1。

#### RAG 排序指标

- `recall_at_k()`；
- `precision_at_k()`；
- `reciprocal_rank()`；
- `ndcg_at_k()`；
- `retrieval_metrics()`：对多条 RAG 用例求平均。

### `evaluation/runner.py`

把指标连接到现有系统组件：

- `evaluate_intent_cases()`：调用 IntentRecognizer，并可选调用路由函数；
- `evaluate_retrieval_cases()`：调用 Retriever，读取返回的 chunk_id，再计算 RAG 指标。

它不会自己发明预测结果，只运行现有的识别器或检索器，然后和人工标注比较。

### `evaluation/evaluator.py`

这是尽量贴近本地 EchoMind 的高级评测器，包含：

- `IntentTestCase`；
- `QualityScores`；
- `EvalResult`；
- `EvalReport`；
- `DEFAULT_INTENT_CASES`：11 条默认 Intent 用例；
- `DEFAULT_DIALOG_CASES`：4 条单轮和 1 组多轮对话；
- `EndToEndEvaluator`。

`EndToEndEvaluator.run()` 会运行 Intent、真实 Orchestrator 对话、LLM Judge、0.75 通过判断、`pass_rate`、`avg_scores`、`recommendations` 和 5% baseline 退化检测。

### `evaluation/judge.py`

提供可选的 LLM-as-Judge：

- `JudgeResult`：四项分数和 rationale；
- `LLMJudge.judge()`：把问题、回答、上下文和参考答案交给模型；
- `LLMJudge.parse()`：读取 JSON 并把分数限制在 0 到 1；
- 模型失败或 JSON 不完整时，按 EchoMind 风格使用 0.5 的保守分数。

它使用项目自己的 OpenAI-compatible `LLMClient`，所以不直接绑定 Anthropic SDK。

### `evaluation/regression.py`

比较新旧报告，默认采用 EchoMind 设计中的 5% 相对变化阈值：

```text
baseline = 0.90
current  = 0.84
相对变化 = -6.67%
→ 标记 regression
```

可以通过 `tolerances` 为某个指标设置不同阈值。

### `evaluation/__main__.py`

支持：

```bash
./.venv/bin/python -m evaluation
```

这个入口默认不启动 Redis、ChromaDB 或模型，只运行本地 Intent 和路由评测，适合快速验证规则是否被改坏。

### `evaluation/data/cases.json`

当前的本地 smoke dataset，包含少量英文 Intent 和路由用例，不是 EchoMind 文档中提到的 500 条真实人工标注集。

### `evaluation/data/`

当前存放评测数据。后续可以增加更大的 Intent 标注集、真实 RAG 查询和相关 chunk_id、带参考答案的端到端对话集。

### `evaluation/__init__.py`

统一导出 Evaluation 的指标、数据结构、Runner、Judge、端到端评测器和回归比较函数，方便其他模块直接从 `evaluation` 包导入。

## 十五、`api/`：HTTP 应用入口

### `api/main.py`

这是 FastAPI 应用的总入口，也是整个运行时的组装位置。

#### `lifespan()`

应用启动时创建共享对象：

- `GET /skills`：查看 Skill 元数据；

- `GET /trace/tool/{request_id}`：查看一次请求的 Tool Trace；

- `GET /metrics`：Prometheus 指标；
- `GET /knowledge/search`：直接搜索知识库；
- `POST /search`：完整检索链路的兼容入口；
- `POST /knowledge/add`：批量添加文档；
- `POST /knowledge/upload`：上传 `.md`、`.txt` 或 `.json`；
- `GET /knowledge/stats`：查看 chunk 数量；
- `POST /eval/run`：运行 Intent、单轮、多轮、LLM Judge 和 baseline 评测；
- `GET /tools/stats`：查看 Tool 可靠性统计。

知识库添加或上传后会尝试刷新 BM25 索引。

### `api/__init__.py`

包说明文件，表明 `api/` 是 HTTP 层 Python 包。真正的 FastAPI 应用对象在 `api/main.py`。

命令行评测和 API 评测的区别是：

```text
python -m evaluation
  → 无模型、无完整 Agent 运行，适合本地规则检查

POST /eval/run
  → 真实调用 Orchestrator 和 Agent，适合完整链路评测
```

例如，EchoMind 文档提到 RAG 召回率，但本地 `evaluation/evaluator.py` 主要实现的是 Intent、端到端对话、LLM Judge 和回归检测；Arclume 现在额外保留了 RAG 的 Recall@K、Precision@K、MRR 和 NDCG 计算框架。

`sources_read/EchoMind/.venv`、`node_modules`、`.git`、ChromaDB 二进制数据和缓存文件不是学习重点，不要把它们当成业务源码逐个阅读。

## 二十二、不应该当作业务源码学习的目录

### `.venv/`

Python 虚拟环境，里面是第三方依赖和解释器文件。

### `frontend/node_modules/`

前端依赖安装目录，里面是 Vue、Vite 和其他第三方包，不是 Arclume 的业务代码。

### `.pnpm-store/`

包管理器缓存。如果它出现在工作区，不应把里面的文件加入项目架构理解。

### `data/chroma/`

ChromaDB 本地持久化数据，是索引和向量数据，不是手写业务代码。

### `__pycache__`、`.pytest_cache`、`.DS_Store`

运行时缓存或系统生成文件，忽略即可。

## 二十三、一次真实请求的完整例子

用户发送：

```text
我的应用登录时一直报 401，应该怎么办？
```

### 第一步：API 接收

`api/main.py` 的 `/chat` 接收 message、user_id 和 conversation_id。

### 第二步：读取 Memory

`ConversationMemory` 从 Redis 读取最近消息、当前 summary、可能相关的 episodic memory 和用户画像。

### 第三步：Intent 识别

`IntentRecognizer` 可能得到：

```text
intent = technical_login
intent_group = technical
entities = {"error_code": ["401"]}
urgency = low
should_use_rag = true
```

### 第四步：Agent 路由

`AgentOrchestrator` 根据 `technical_login` 选择：

```text
primary_agent = technical
```

### 第五步：选择 Skill

`SkillLoader` 选择 `skills/technical/SKILL.md`，因为当前 Agent 是 technical，且用户消息包含 login。

### 第六步：RAG

Technical Agent 通过 `knowledge_search` 调用 ToolManager，产生原查询和若干本地变体，然后 Dense 与 BM25 并行召回 `technical_support.md` 中的相关 chunk，再融合、去重和重排。

### 第七步：构建 Context

`ContextBuilder` 将当前问题、历史、AgentState、technical Skill、401 相关知识 chunk 和必要的 Tool 结果放入模型上下文。

### 第八步：模型回答

Technical Agent 提供安全排查步骤，例如检查凭证、重新登录、重置密码或更新应用，并且不索要密码或验证码。

### 第九步：Trace 和 Memory

系统记录 request_id、Intent、路由、RAG、Tool、Agent 耗时和请求结果；Assistant 回复写回 Redis，必要时触发 Memory 压缩。

## 二十四、如何启动和检查项目

### 1. 配置环境

```bash
cp .env.example .env
```

填写真实模型配置：

```text
LLM_API_KEY=...
LLM_BASE_URL=...
LLM_MODEL=...
```

### 2. 启动基础设施

如果使用 Docker：

```bash
docker compose up -d --build
```

它会启动 Redis、ChromaDB、API、Prometheus 和 Nginx。

### 3. 本地启动 API

```bash
./.venv/bin/python -m uvicorn api.main:app \
  --reload \
  --host 127.0.0.1 \
  --port 8000
```

### 4. 检查服务

```bash
curl http://127.0.0.1:8000/health
```

如果显示 `{"status":"ok","service":"arclume-api"}`，说明 HTTP 服务已经启动。`llm_configured=false` 只说明模型没有配置，不代表 FastAPI 没有启动。

### 5. 直接测试知识库

```bash
curl "http://127.0.0.1:8000/knowledge/search?query=How%20long%20does%20a%20refund%20take&top_k=5"
```

这条路径不需要客服大模型，但需要 KnowledgeBase 可用。

### 6. 运行无模型评测

```bash
./.venv/bin/python -m evaluation
```

### 7. 运行完整评测

API 启动并且模型配置好以后：

```bash
curl -X POST http://127.0.0.1:8000/eval/run
```

### 8. 启动前端

```bash
cd frontend
npm install
npm run dev
```

浏览器打开 Vite 显示的地址，默认通常是 `http://127.0.0.1:5173`。

## 二十五、遇到问题时应该看哪里

### `curl: Failed to connect to 127.0.0.1 port 8000`

说明 API 进程没有启动，或者端口不是 8000。先启动 Uvicorn，再运行 curl。

### `/health` 正常但 `/chat` 503

常见原因：

- LLM_API_KEY、LLM_BASE_URL 或 LLM_MODEL 没配置；
- Redis 不可用；
- 模型接口返回错误。

### `/health` 中 `knowledge_base.ready=false`

说明 ChromaDB 不可用或本地 Fallback 没有开启。此时 API 可以启动，但 RAG 不能正常提供知识结果。

### RAG 只有 dense，没有 BM25

检查：

- `ARCLUME_RAG_BM25_ENABLED=true`；
- BM25 索引是否初始化；
- 知识库是否已经写入文档；
- `/health` 中 `rag_bm25_documents` 是否大于 0。

### 没有看到模型查询改写

默认是本地查询改写，目的是方便测试和节省 Token。要使用 LLM 查询改写，需要：

```text
ARCLUME_RAG_LLM_ENABLED=true
```

同时必须正确配置模型。

### `/eval/run` 评分很多是 0.5

通常表示 LLM Judge 没有配置、Judge 请求失败或模型返回的 JSON 无法解析。这是保守回退分数，不代表 Agent 的真实质量就是 0.5。

## 二十六、最终记忆版

如果只记住每个目录的一句话，可以记成：

```text
api/          HTTP 入口和依赖组装
schemas/      共享数据结构和接口契约
core/         模型传输、Intent、Context、Skill 加载
harness/      Tool 权限、执行、循环和 Trace 边界
knowledge/    ChromaDB、BM25、Hybrid RAG 底层
tools/        Tool 函数和完整 RAG / Tool 编排
memory/       Redis 工作记忆、ChromaDB 长期记忆、AgentState
skills/       人工维护的业务规则和安全规范
agents/       Agent 角色、回复逻辑和多 Agent 路由
monitor/      线上运行健康监控
evaluation/   离线质量评测、Judge 和回归检测
data/         默认知识库文档
tests/        自动化验证
config/       Nginx 和 Prometheus 部署配置
frontend/     Vue 调试界面
docs/         分阶段学习和开发说明
sources_read/ 本地 EchoMind 参考资料，不是 Arclume 运行时代码
```

最重要的模块关系是：

```text
IntentRecognizer 决定“用户想做什么”
AgentOrchestrator 决定“谁来处理”
CustomerServiceAgent 决定“怎么构建一次回答”
ContextBuilder 决定“把什么材料交给模型”
ToolManager 决定“怎么检索和管理工具”
Harness 决定“工具是否允许安全执行”
Memory 决定“记住什么”
Skill 决定“遵守什么业务规范”
Monitor 决定“运行是否健康”
Evaluation 决定“修改后是否变好”
```
